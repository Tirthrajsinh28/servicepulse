# ServicePulse Interview Guide

Status: Living guide; update after every verified slice.

## Problem and users

ServicePulse gives fictional development teams a reliable record of services, incidents, owners, lifecycle events, comments, and audit history. Administrators manage workspaces; responders operate incidents; viewers inspect state.

## Architecture

It is a Spring Boot modular monolith designed for PostgreSQL with a
React/TypeScript client. Package-by-feature backend modules and a typed frontend
API boundary preserve separation without the operational cost of premature
microservices.

## Database and main entities

The schema contains users, workspaces, memberships, managed services, incidents, incident events, comments, and audit entries. UUIDs are generated by the application. Foreign keys and check constraints protect tenant and workflow data.

## Authentication

Enabled database users authenticate with email and BCrypt password hashes. A
local failed-login limiter counts repeated failures by normalized email address
and returns the same generic authentication error when the threshold is reached.
The server issues a short-lived HMAC-signed JWT and an opaque random refresh
token. Only the refresh token's SHA-256 hash is stored. Refresh exchanges rotate
and revoke the prior token; logout revokes it. The signing secret has no
application default.

## Authorization

The first incident API uses database-backed workspace membership:

- Administrator/responder: declare an incident.
- Administrator/responder: transition an incident.
- Administrator/responder: assign an eligible responder and add a comment.
- Administrator/responder/viewer: retrieve an incident, comments, and its event timeline.

Cross-workspace incident creation, viewer mutation, disabled-member access, and ineligible assignment are denied in tests. Membership administration and role-change audit records remain.

Managed-service creation/updates and membership mutations require an enabled administrator role. Responders and viewers may list services and members but cannot mutate either. Ordered membership locks preserve at least one enabled administrator.

## API design

- Versioned `/api/v1` routes.
- Jakarta validation at the request boundary.
- `ProblemDetail` responses for validation, not-found, invalid-transition, and authorization errors.
- Location header on creation.
- Explicit transition subresource at `/api/v1/incidents/{id}/transitions`.
- Read-only chronological event timeline at `/api/v1/incidents/{id}/events`.
- Idempotent assignee resource at `/api/v1/incidents/{id}/assignee`.
- Comment collection at `/api/v1/incidents/{id}/comments`.
- Workspace-scoped incident collection with text/service/status/severity filters.
- Bounded page envelope instead of exposing Spring's internal page representation.
- Workspace dashboard summary built from aggregate queries.
- Workspace-nested service collection/item routes with immutable slugs.
- Workspace-nested membership collection/item routes with explicit POST/PUT/DELETE semantics.
- Authenticated workspace directory so clients discover tenant IDs without hard-coded configuration.
- Administrator-only failed-notification inspection with stable, bounded pagination.
- OpenAPI generated from the implementation.
- OpenAPI identifies the project/build version, documents the bearer JWT
  boundary globally, and marks only login, refresh, and status as public.

## Error handling

Business exceptions are translated centrally. Responses avoid stack traces and sensitive configuration. Validation errors identify fields without echoing secrets.

## Background processing

Incident declarations and status transitions enqueue a notification outbox row in their database transaction. The scheduled worker claims bounded batches, invokes an adapter with the stable job ID, retries with capped backoff, reclaims stale processing jobs, and retains exhausted jobs as `FAILED`. The current adapter only emits a structured local log. Delivery is at least once, so a real adapter must deduplicate by notification ID.

Exhausted jobs receive a failure timestamp and are visible through a
workspace-administrator endpoint. The page is tenant-scoped and reveals only a
sanitized exception class, never uncontrolled exception messages or incident
content. Administrators can replay a failed job through a separate endpoint
that preserves the job ID, resets attempts and failure fields, writes an audit
entry, and returns the row to `PENDING` for the worker. The operator request
does not call an external delivery provider directly.

## Deployment and monitoring

Deployment has not been selected or executed. The foundation includes Actuator health, Prometheus registry support, native JSON console logs, and request correlation. External dashboards, deployment health verification, and rollback documentation remain.

## Security

- Secure-by-default route policy.
- No generated default user.
- No hard-coded production credential.
- Method role checks.
- Input validation.
- Deliberately minimal public operational surface.
- Bounded request IDs with UUID replacement for invalid client values.
- MDC cleanup and no request-body/query/authorization logging in the correlation filter.
- Last-enabled-administrator protection under a deterministic membership lock order.
- Local failed-login throttling with generic error responses.
- Exact-origin CORS allowlist that defaults to no cross-origin browser access.
- Access token kept in memory and refresh token limited to tab-scoped
  `sessionStorage`, with the XSS trade-off documented.
- One refresh/retry attempt rather than an unbounded authentication loop.

Distributed/shared-store rate limits, database-level audit immutability, secret
rotation procedures, content-security policy, and broader security tests remain
incomplete.

## Current challenges

- Keeping token identity separate from workspace roles so role changes take effect without waiting for token expiry.
- Testing PostgreSQL-specific behavior without local Docker.
- Keeping incident state, comments, its event timeline, and audit record atomic.
- Keeping correlation data available through completion logging and removing it before thread reuse.
- Flushing the incident before the JDBC outbox insert while preserving one transaction.
- Handling the acknowledgement gap with a stable idempotency key and stale-claim recovery.
- Making terminal failures observable without leaking payloads, and replayable
  through an audited reset rather than direct operator-triggered delivery.
- Keeping a browser session usable across access-token expiry without persisting
  the access token or creating an unbounded retry loop.
- Translating append-only assignee IDs into current friendly member names
  without changing the backend audit record.

## Trade-offs

- Modular monolith over microservices: lower operational overhead, deeper completion.
- H2 plus Testcontainers: fast feedback without pretending H2 equals PostgreSQL.
- IDs across feature packages: less convenient than object graphs, but clearer boundaries.

## Known limitations

See the repository README. The largest gaps are external notification delivery,
registration/invitations, distributed/edge abuse controls, broader frontend

## Two-minute explanation

ServicePulse is an independent incident-management platform I am building to
demonstrate engineering beyond CRUD. It uses a Spring Boot modular monolith
designed for PostgreSQL and a React/TypeScript client. The core domain includes
workspaces, memberships, services, incidents, lifecycle events, comments, audit
records, and a notification outbox. I chose a modular monolith so I could go
deeper on transactions, authorization, testing, and operations without adding
unnecessary network failure modes. The local browser flow covers sign-in,
dashboard queries, declaration, transition, assignment, and comments. The
notification adapter logs locally only; I do not claim a live external
integration. Fast tests use H2 in PostgreSQL mode, while Testcontainers remains
the real database gate and is blocked locally because Docker is unavailable.

## Demonstration script

Current local demonstration:

1. Run `mvnw.cmd test`, then `npm.cmd run check` under `frontend`.
2. Start the API with a local-only development password and start the Vite client.
3. Sign in and show that the workspace ID/role comes from the API.
4. Declare a synthetic incident and show the event/audit/outbox transaction.
5. Transition and assign it, then add a comment.
6. Show friendly browser labels while explaining that the persisted event remains ID-based.
7. Search by text/status/service, then show page metadata and dashboard totals.
8. Show viewer mutation denial in the automated tests.
9. Create a managed service and show idempotent audit behavior in its API test.
10. Attempt to remove the last enabled admin and show the conflict test.
11. Fail a notification once, rerun the worker, and show the same job ID delivered.
12. Show the admin failed-job page, replay endpoint, and responder/other-workspace denial tests.
13. Send a known request ID and correlate the response header with the JSON log.
14. Explain why `mvnw.cmd verify` remains blocked without Docker and why H2
    results are labeled as a substitute.

## Likely interview questions

- Why not microservices?
- Why use both database constraints and Java validation?
- How will workspace authorization prevent IDOR?
- How do optimistic locks affect incident updates?
- Why is H2 insufficient?
- How would refresh-token rotation work?
- How are incident state, timeline events, and audit entries kept consistent?
- How would you strengthen append-only guarantees at the database boundary?
- How do search and dashboard queries preserve tenant isolation?
- Why escape `%` and `_` in user-supplied search text?
- Why make service slugs immutable, and how does the database handle duplicate races?
- Why validate client request IDs, and why must MDC be cleared?
- Why lock membership rows in a consistent order?
- Why does the last-admin check ignore disabled accounts?
- Why is an outbox better than calling a notification API inside the incident request?
- Where can at-least-once delivery duplicate work, and how should an adapter respond?
- Why does failed-job replay return work to the worker instead of calling the
  adapter directly?
- What would trigger a future service split?

## Honest answer framework

Use: what exists, how it was verified, what remains, and the next defensible improvement. Never imply production users, employer ownership, a live deployment, or PostgreSQL integration results that have not been observed.
